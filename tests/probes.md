# qwork 冷启动探针（回归清单）

> 每次改动 `SKILL.md` / `SCHEMA.md` / `templates/` 后手跑一遍。只验一件事：**冷启动执行者会不会回来问**。

## 怎么跑

1. 新开子代理或新会话，先 `skill` 加载 qwork，要求真读文件；**只读，不改任何文件**。
2. 只给场景，不提示答案；让它输出「完整行动序列 + 缺口（按严重度）+ 总评（能/勉强/不能）」。
3. 三个场景分别跑；结果记到文末表格。

> 4.3.0 收口项跑了 4 次：前两次暴露「收口清单 / 状态符号 / 流转图」与阻塞收口的字面冲突，修复后终验为「能」。这类冲突只有冷启动复跑能发现。

## 场景 1：新建（基线未知）

> 项目是 git 仓，根目录已有 `0_workbench/`（spec.md、design/、change/、archive/）。用户说：
> 「新建一个 change，做 WiFi 驱动 RX 吞吐优化，目标比基线提升 10%」

看：基线未知时怎么定标准、check 是否可执行、tasks 是否有判据与接手须知、何时提交。

## 场景 2：收口（真实仓只读）

> 给你一个 `0_workbench/change/<name>/`：tasks 声称都打勾，但实际有 `[ ]` 阻塞项；`0_workbench` 缺 spec.md/design/archive；且已被 git 跟踪。用户说：
> 「tasks 都打勾了，帮我收口归档吧」

看：是否先自查 tasks、能否识别骨架缺失、归档是否用 `git mv`、ignore 路径是否复核、阻塞是否走「用户确认的阻塞收口」。

> 追加问：tasks 全勾但没有「收口」段，算不算完结？（4.6.0 起：不算——tasks 全勾含收口段才算完结，先补收口段。）

## 场景 3：改需求

> 已有 change：spec 目标 `≥ 基线 ×1.10`，check 已写好，P0/P1 完成、P2 未开始。用户说：
> 「目标改成提升 15%，其他不变，继续做」

看：是否同步 spec/check/tasks/design、是否写变更记录、已完成阶段是否重开、是否做可行性核对。

## 评分口径

- **能**：照技能即可完成；按设计需要用户确认的（如 change 命名、阻塞收口、项目约束来源）不算缺口。
- **勉强**：能走通，但有 1–2 处要靠经验或规范外的裁决。
- **不能**：照技能会做错或卡死。

## 结果记录

| 版本 | 新建 | 收口 | 改需求 | 说明 |
|---|---|---|---|---|
| 4.0.0 | 勉强 | 不能 | 勉强 | 首轮；check 勾选载体、git mv、阻塞收口均缺失 |
| 4.2.0 | 能 | 勉强能 | 能 | 三轮修复后；骨架内容/知识库落点仍需外推 |
| 4.3.0 | 能 | 能 | 能 | who/when 字段 + 黄金样例；收口经 4 次复跑，前两次的字面冲突已修 |
| 4.6.2 | 勉强 | 不能 | 勉强 | 冷启动复跑；status/check 均提示行内阻塞；混合态/证据自洽/提交范围仍缺 |

> 4.6.2 冷启动要点：新建场景卡在“目标代码/实验环境不在仓 + 提交范围无约束”；收口场景卡在“`[ ]` 阻塞 + 证据自洽 + 混合态阻塞写法”；改需求场景卡在“可行性核对无输入 + 复用结论前未验证据 + check 阈值副本无门禁”。
