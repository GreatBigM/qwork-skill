# 执行交接与子代理手册

> 按需加载：SKILL.md §3/§4/§6 只放铁律，本文件是完整做法。
> 适用：派执行会话/子代理、长任务等待、闭环回报核验、并发写同一 change。

## 一、失败熔断（执行细节）

铁律见 SKILL.md §3：同一任务连续失败 3 次即停，不许第 4 次自动重试。

- **报告内容**：① 已尝试的 3 次各是什么（参数/方法/命令）② 每次失败的具体现象（错误信息/串口输出/exit code）③ 判断（参数错误？环境问题？方法不可行？）④ 下一步建议（需用户决策的选项）。
- **为什么必须有熔断**：没有熔断会陷入「失败→换参数→再失败」循环，消耗大量 token 无法收敛。设备半死/串口无输出/网络不通需要人工介入（断电/连线/配网），自动重试无法解决。3 次足够覆盖「参数错误修正」，超出说明问题不在参数层面。
- **熔断后恢复**：用户介入处理后告知「可以继续」，从断点继续，失败计数清零。
- **参数错误主动检测**：错误参数（波特率/路径/IP）时进程常持续运行不报错（能 write 但 read 乱码/空），不能被动等超时——执行后主动检查（烧录类 `fuser /dev/ttyUSB0` + `ps aux | grep auto-uboot`；编译类 `ps aux | grep make` + 查日志），发现错误先 `kill -9` 释放资源（串口/终端）再重试。

## 二、对话分离模式

将「无限长的模糊上下文」转化为「有限、确定的执行单元」。核心原理：**两个对话之间只传文件（工件），不传历史（聊天记录）。**

```
规划会话              解耦期              执行会话（新对话）      反馈期（规划会话）
┌──────────────┐    ┌──────────┐    ┌──────────────┐    ┌──────────────┐
│ 分析 + 设计   │ → │ 产出物化  │ → │ 只读 tasks    │ → │ 读阻塞原因    │
│ 冻结工件      │    │ design   │    │ 逐条勾选执行   │    │ 标注原因      │
│ >3模块拆      │    │ tasks    │    │ 遇阻塞→退出   │    │ 修正设计      │
│ 提示退出      │    │ constr.  │    │ 严禁改设计文档  │    │ 产出 v2       │
└──────────────┘    └──────────┘    └──────────────┘    └──────────────┘
```

- 规划会话：讨论定稿，产出 spec/design/tasks/check 工件（本 skill 四要素）。
- 解耦期：工件是唯一跨对话载体。
- 执行会话：新对话只读 tasks 逐条执行，遇阻塞立即退出（不自行改设计），严禁执行中改设计文档。
- 反馈期：阻塞原因带回规划会话，修正设计产出 v2，再开新对话。

## 三、执行载体：新窗口会话 或 子代理

**二选一（用户明确偏好）**：新开窗口执行会话，或**派遣子代理执行**（主 agent 控制主对话流程与决策，子代理执行带回结果）。

子代理分工铁律：

- 子代理只做实测+分析，**带回数据与建议（≤500 字摘要），不 commit 源码、不归档、不写知识库**——方向性决策（合入/删除/归档收尾/判据修订）留在主对话；工作区终态二选一明确报告（改动留工作区未 commit / 恢复基线干净）。
- **设备重活按里程碑拆**：平台有硬性时长/调用上限（Hermes delegate 实测 ~900s / ~50 calls；DSH `subagent` 无该固定值，但同样宜一代理一里程碑）。编译+烧录切换+短矩阵+600s 长稳+A 同窗复测整包必超限（gro-mainpath-ab 连续 3 个子代理截断教训）。一代理一里程碑（如「烧 B + B 短轮矩阵」/「B 300s×2 长稳」/「烧 A + 同窗复测」），靠落盘 `change/data/` 接力断点。
- **等待用平台的后台能力**：DSH = `bash` 的 `run_in_background` + `job_output`；Hermes = `execute_code` sleep 循环保 adb 会话（裸 `&` 后台会在会话断开被杀）。
- **超时/截断 ≠ 白跑**（kernel-515 P2 裁剪盘点 2026-09-07 实证）：勘察型 agent 超时无 summary 时，平台若保留 live transcript（Hermes 示例 `~/.hermes/cache/delegation/live/<deleg_id>/task-0.log`）常含**完整定量数据**（裁剪省字节表 8 项全在，仅收尾汇总未写）——`tail` + `grep -oE` 关键输出模式提取即得，任务 90% 完成勿重派，只补缺的收尾段；transcript 尾部连续慢全仓 grep（跨仓 -r 无排除 116-180s/次）是超时主因——给子代理任务限 grep 范围（路径排除/maxdepth）。
- **给子代理完整环境与现成通道，禁止探索**：设备 IP 动态现查（重启必换，/23 扫 5555 + uptime 辨识）、烧录走 adb-tftp 的 `mai_auto_flash.sh` original mode（勿自建 TFTP——宿主 sudo 密码子代理没有）、重启后 /tmp 清空重推工具。
- 子代理结果回来仍走 §五 核验三查。

| 需要 | DSH | Hermes（对照） |
|---|---|---|
| 起子代理 | `subagent` / `subagent_fork` | `delegate` |
| 后台长任务 | `bash` + `run_in_background`，`job_output` 取结果 | `execute_code` sleep 循环 |
| 等完成 | 轮询产物/标记或等完成通知，不空转 | 同 |

## 四、长任务 / 长等待纪律

（2026-10-24 实证：多睡 7.5min 才发现已完成）

1. **只留一个权威 job**：同机并发多条 soak（不同 change 各起一遍）会互相打断、抢设备窗口，「进行中」记录过期。一轮长测供多个 change 共用证据，并在各 change 写**证据映射表**，别各烧各测。
2. **末片 sleep 必须对齐已知终点**：`for i in $(seq N); do sleep 1740; done` 这类轮询若片长乘片数越过终点（3×1740 + 尾片 1700 > 2h），会多等一整轮。以「结束时间 - 当前时间」算最后一片，或直接轮询完成标记。
3. **判完成靠产物/标记，不靠时长**：`SOAK_DONE` 文件、`Written: OK`、`partition PASSED`、日志末行时间戳到点，任一命中即推进；等待期不新增竞争唤醒源。
4. **长任务一律 background + notify**：前台 sleep 链会被会话超时/中断打断，且中途无法做别的判断。

## 五、闭环声明核验三查

执行会话（独立窗口/子代理）回报「闭环/归档完成」时，tasks/check 的 `[x]` **不可直接采信**。实测实例（2026-09-05 filter-tcp-ack-ab）：执行会话把「知识库沉淀 commit + change 归档」勾成 `[x]`，实际三项全虚标——知识库 git log 无该 commit、change 目录未移 archive/、驱动源码改动也未 commit。

接收闭环回报后**核验三查**（缺哪项补哪项并回填漏勾的 tasks）：

1. **源码 commit**：驱动仓 `git log --oneline -5` 最近提交含该 change（本地 commit 绝不 push；A/B 合入 change 最容易漏这一步——测试跑完源码没提交）。
2. **知识库沉淀**：`cd <知识库根> && git log --oneline -3`；`rg -l "<change>" .` 能定位到对应产出（命名按知识库侧规则）。
3. **归档**：`change/<name>` 已不存在 + `archive/<name>` 存在 + 项目级 spec.md 变更记录有该 change 行。

## 六、并发会话双写防护

workbench 工件可能不在 git 仓下（也可能在：实例 pilot-repo 就是 git 仓且已跟踪 `0_workbench/`）——先 `git -C <项目根> ls-files 0_workbench | head -1` 判断有没有 diff 可恢复；不在 git 下则双写**不可恢复**。

- **写前查并发**：`ls -lat 0_workbench/change/<name>/` 看目标目录最近改动时间戳（秒级新鲜 = 可能有他方在写）+ 平台是否报告 sibling 修改（DSH 工具会提示 "modified by sibling subagent ... but this agent never read it"）。**DSH 多会话在同一进程，`ps aux | grep hermes` 这类进程探测无效，别用。**
- **新建 change 前查重**：`ls 0_workbench/change/ 0_workbench/archive/` 找同主题已存在 change——先确认是补全还是新建，避免重复规划。
- **撞 sibling 警示即停**：不要静默覆盖——停下向用户报告（哪个会话可能在规划同一 change），请用户裁定所有权后以一方为准；继续覆盖会把对方未落盘的规划丢进黑洞。
- **归档/闭环同理**：移 archive/ 前先复核目录归属，防止把别的会话正在施工的 change 误移。
